# 17 – 7x6 on a 32 GB machine: fits on paper, not next to a desktop session

## Idea

The first goal of this work was to run the 7x6 strong solve, which needed 128 GB, on a
32 GB Mac. The measurements in [16](16-sizing-ladder.md) say what it takes:

| | nodes | bytes |
|---|---:|---:|
| largest per-ply `W + D + L` (ply 29, known from the published solution) | 1.14 G | |
| alive at the peak, 1.06 x | 1.21 G | 19.3 GB of nodes |
| unique table buckets (2^30) | | 4.3 GB |
| operation cache (2^28 entries) | | 4.3 GB |
| **total with the default table layout (`28G`, 1.34 G nodes, 90 % full)** | | **28 GiB** |

Two options were added to trade speed for memory, because 28 GiB of 32 is uncomfortable:

* `BUCKET_SHIFT=n`: the unique table gets `2^n` times fewer buckets (longer chains);
* `CACHE_SHIFT=n` (existing): a smaller operation cache.

With `BUCKET_SHIFT=1 CACHE_SHIFT=3` the same 1.34 G nodes fit into a `24G` budget
(19.2 bytes per node).

A third option, `IN_OP_GC_GROWTH=g` (off by default), triggers GC during operations
when more than `g` times the nodes alive after the last GC are allocated, not only when
the pool is 90 % full. Without it a single large operation fills the pool with garbage
up to the 90 % mark regardless of how little is alive (the run below had 742 M nodes
allocated with 237 M alive), so the process always grows to the full table size.

## Justification

The requirement is dominated by the live nodes (19.3 GB), which no setting changes.
Buckets and cache are the only parts that can give. Halving the number of buckets
doubles the chain length, i.e. about half an extra memory access per unique-table
lookup; a cache that is small relative to the BDDs costs recomputation. Neither was
measured at this size.

## Experimental results

**The attempt.** `solve.out 28G 7 6`, built with `SAVE_BDD_TO_DISK=0` (a full solution is
118 GB), on the M2 Pro with 32 GB while the usual desktop applications were open.

| phase | result |
|---|---|
| forward pass, all 43 reachable sets | 586 s (written to disk: 5.6 GB) |
| retrograde plies 42–38 | 6 s, 16 s, 31 s, 60 s, 104 s |
| ply 37 (`W+D+L` 187 M nodes) | 217 s |
| ply 36 (261 M) | 332 s |
| ply 35 (386 M) | 1249 s |
| ply 34 (491 M) | not finished, run stopped |

The win / draw / loss / terminal counts of plies 42–35 are identical to the published
table (`python3 scripts/regress.py --check ...`).

From ply 35 on the machine ran out of physical memory: 54 MB free, 8–9 GB in the memory
compressor, and the share of system time in the solver's CPU time rose from 19 % to
over 60 %. At that point the solver had touched about 20 GB (12 GB of nodes, 8.6 GB of
buckets and cache). After the run was stopped, 6 GB of compressed memory (14 GB
uncompressed) belonging to the other applications remained, plus 2.3 GB wired.

So the limit on this machine, as it is normally used, is about **21 GB** for the solver,
not 28. The 7x6 solve needs 24 GiB even with the reduced tables. It was not completed.

**What is established**

* The algorithmic requirement, 1.06 x the largest `W + D + L`, measured on 6x5 and 6x6
  with tight tables, gives 1.21 G nodes for 7x6. The original run needed a table of
  2^31 nodes at 53 bytes (114 GB) and was thrashing at 90 % fill.
* On the 128 GB machine the solve now needs a quarter of the memory (`28G`) and, going
  by 6x6 (4.2x faster with the same table, 2.5x faster in a table one fifth the size),
  should take well under half of the original 47 hours.
* On a 32 GB machine it fits only if the solver can have 24–28 GiB to itself.

**Ways to finish it on the Mac**

1. Run it with the other applications closed (or after a restart), with the reduced
   layout:

   ```
   cd src/connect4
   make solve SAVE_BDD_TO_DISK=0 BUCKET_SHIFT=1 CACHE_SHIFT=3
   ./build/solve.out 24G 7 6
   ```

   Expected run time: of the order of ten hours, extrapolated from 6x6 in a tight
   table (2.7 s per million `W+D+L` nodes; 7x6 has 13 billion in total).

2. Shrink the node itself: done afterwards as an optional layout, see
   [18](18-compact-node-layout.md). With `COMPACT_NODES=1` the run needs about 19 GB.

## Addendum: the completed run

Run on the same Mac with all other applications closed, default layout,
`make solve SAVE_BDD_TO_DISK=0 BUCKET_SHIFT=1 CACHE_SHIFT=3`, `solve.out 24G 7 6`
(1.342 G nodes, 25.8 GB; the solution files were not written):

| | |
|---|---:|
| total time | 67,917 s (18.9 h) |
| forward pass | 545 s |
| GC time | 5,787 s (8.5 %), 114 collections during operations |
| largest number of nodes alive after a GC | 1,233,682,906 (1.08 x the largest `W + D + L`) |
| largest fill level of the table | 95.96 % |

All 43 plies have exactly the win / draw / loss / terminal counts of the published
solution. The table was only just large enough, which cost time: the plies around the
peak ran at 6–6.5 µs per result node, the ones without memory pressure at 2–4 µs.
For comparison, the original run took 47 hours on a 128 GB machine.
